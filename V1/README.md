# 基于哈希映射的多种定长内存分配器（内存池）

> C++11 实现 · v1 版本 · 无第三方依赖

本仓库实现一种**基于哈希映射的多种定长内存分配器**（内存池的一种）。它一次性向系统申请大块连续内存，然后在池内按固定大小切成小块反复使用，从而避免高频 `new`/`delete` 带来的系统调用与内存碎片。

---

## 术语约定

| 术语  | 含义                                                             |
|-------|------------------------------------------------------------------|
| Chunk | **大块内存**：一次向系统申请的整段连续内存（默认 4096 字节）        |
| Block | **小块内存**：池内按固定大小切分的最小分配单元，直接交给使用者      |

```text
Chunk（系统申请，4096 字节）
┌────────┬────────┬────────┬────────┬─────┐
│ 头(链) │ Block  │ Block  │ Block  │ ... │
└────────┴────────┴────────┴────────┴─────┘
          └─ 每个 Block 为定长小块（如 8 / 16 / ... / 512 字节）
```

---

## 设计逻辑

### 1. 总体架构：HashBucket → 64 个定长池

请求分配时，把**请求字节数**映射到某个定长池，即"哈希映射"：

```
池下标 index = ⌈size / 8⌉ - 1
```

- 请求大小 ≤ 512 字节：按 8 字节向上取整，落入 64 个池之一
  （池 0 服务于 1~8 字节，池 1 服务于 9~16 字节，……，池 63 服务于 505~512 字节）
- 请求大小 > 512 字节：直接交给系统分配器 `operator new` / `operator delete`

```text
HashBucket::allocate(size)
        │
        ├── size > 512 ────────────────► operator new(size)
        │
        └── size ≤ 512 ──► pool[index] ──► 从对应定长池取一个 Block
```

### 2. 单个定长池（MemoryPool）内部结构

每个池只服务一种 Block 大小，池内维护三种资源：

```text
MemoryPool（Block 大小 = N 字节）
│
├─ Chunk 链表        firstChunk_ ──► Chunk1 ──► Chunk2 ──► ...   （析构时统一回收）
├─ 空闲 Block 链表   freeListHead_ ──► 已释放可复用的 Block（先进后出栈）
└─ 未用区游标        nextUnusedBlock_ ──► 当前 Chunk 中尚未划出的连续区
```

- **Chunk 链表**：每个 Chunk 头部存一个指向前一个 Chunk 的指针，串成链表。
  析构时沿此链表把全部 Chunk 归还给系统。
- **空闲 Block 链表**：Block 被释放后进入此栈。此时该 Block 的内存不再被使用，
  其**头部 8 字节恰好存放"下一个空闲 Block"的指针**（各池 Block ≥ 8 字节，放得下指针）。
- **未用区游标**：新 Chunk 中按 Block 大小连续切分，游标逐块前移；
  游标到达 Chunk 末尾时，说明该 Chunk 耗尽，再申请新 Chunk。

### 3. 分配流程（allocate）

1. 从空闲 Block 链表**栈顶取一块**（优先复用，避免浪费）；
2. 若空闲链表为空，从未用区游标处**划出一块**并前移游标；
3. 若当前 Chunk 余量不足一个 Block，先向系统申请一个新 Chunk（`operator new`），再接步骤 2。

一次系统申请（一个 Chunk）可服务上百次分配，后续分配均为 O(1) 的指针操作。

### 4. 释放流程（deallocate）

把 Block 重新挂到空闲链表**栈顶**即可，只有简单的指针赋值，O(1)。

### 5. 布局与对齐

- Chunk 头部 `sizeof(Chunk*)` 字节存放链表指针；
- 负载区起点按 **Block 大小对齐**；
- 由于各池 Block 大小为 8 的幂次倍数，对齐后按 Block 大小连续切分**不会产生缝隙**，
  池内无内部碎片。

### 6. 线程安全

- 每个定长池持有一把互斥锁 `poolMutex_`，保护该池全部状态；
- 不同大小的池各自持锁，**互不干扰**（64 个池天然分散锁竞争）；
- `HashBucket::initialize()` 使用 `std::call_once`，可重复调用且线程安全。

> **工程取舍说明**：早期版本的空闲链表采用无锁（CAS）栈写法。无锁栈在
> "缓存行上的 ABA 场景"下存在指针环回的隐患，在没有安全内存回收机制
> （标记指针 / hazard pointer）时并不真正正确。本版本改为互斥锁保护的
> 先进后出栈——**正确性优先**，代价是同一池内的分配/释放在高竞争下会排队。
> 如需极致并发，可在此基础上演进为"每线程缓存（ThreadCache）+ 中心缓存
> （CentralCache）"的两级结构（见仓库 v2 / v3 版本）。

## 关键点

1. **定长切分，O(1) 分配/释放**：无系统调用、无空闲链表遍历，路由与取块均为常数时间。
2. **空闲复用优先**：释放的 Block 先进后出（栈顶复用），同一地址刚释放即可能被再次分配，
   缓存友好。
3. **一次申请，多次服务**：一个 4096 字节的 Chunk 可服务大量小块分配，显著降低
   系统调用次数与内存碎片。
4. **哈希路由**：任意请求大小按 8 字节向上取整映射到 64 个池之一，选择"够用且最小"的池，
   内部碎片最多 < 8 - 1 字节。
5. **对象级接口**：`newElement<T>(args...)` 在池内内存上定位构造（placement new），
   `deleteElement<T>(p)` 先显式析构再归还内存，类型安全。
6. **使用约束**（使用者需遵守）：
   - 使用前必须调用 `HashBucket::initialize()` 一次（可重复调用）；
   - 归还大小须与分配大小一致（`deleteElement` 自动携带 `sizeof(T)`）；
   - 不检测越界写与双重释放；
   - 池的析构不会修正"仍被使用者持有的指针"，使用者须保证先归还再退出。

## 运行方式

要求：CMake ≥ 3.10、支持 C++11 的编译器（GCC / Clang / MSVC 均可）。

### Windows（Visual Studio / MinGW）

```bash
cmake -S v1 -B v1/build -DCMAKE_BUILD_TYPE=Release
cmake --build v1/build --config Release
v1\build\Release\MemoryPoolProject.exe
```

### Linux / macOS

```bash
cmake -S v1 -B v1/build -DCMAKE_BUILD_TYPE=Release
cmake --build v1/build -j
./v1/build/MemoryPoolProject
```

### 输出说明

程序先运行**正确性测试**（构造析构、对齐、释放复用、大对象直通系统分配器、万级分配压力自检），
再对比**内存池**与**系统 new/delete** 的耗时。

> 说明：示例中的"分配后立即释放"微基准在当代平台（如 glibc / MSVC 的 tcache 类快速路径）上
> 对系统分配器非常有利，两者差距不大甚至系统更快，这属正常现象。内存池的优势体现在：
> 大量**持有型**分配（先批量申请、后批量释放）、缓解内存碎片、分配开销稳定可预测的场景。
